## Problem Statement

`meter proxy` only knows two providers, hardcoded in `packages/proxy/src/routes.ts`: anthropic (`/v1/messages` → api.anthropic.com) and openai (`/v1/chat/completions` → api.openai.com). The builder needs to capture traffic to NVIDIA's hosted endpoint (`integrate.api.nvidia.com`, OpenAI-compatible) today, and the same wall exists for every other OpenAI-compatible host: Groq, Together, Fireworks, Mistral, OpenRouter, Ollama, vLLM, LM Studio. The existing `--openai-target` override forwards correctly but mislabels captured runs as "openai" (in run-title fallback and logs — steps carry no provider field today) and displaces real OpenAI for the session.

Verbatim need: "I have a need right now to point it at the Nvidia upstream."

## What Makes This Cool

One tiny mechanism makes Meterbility the neutral flight recorder for any OpenAI-compatible (or Anthropic-compatible) backend:

```bash
meter proxy --upstream nvidia=https://integrate.api.nvidia.com
# → http://127.0.0.1:8765/nvidia/v1/chat/completions
```

Because the proxy is pure passthrough (auth forwarded, never persisted; bodies untouched), a "provider" reduces to three fields: **name → upstream URL → capture dialect**. No model routing, no key management, no protocol translation — the machinery that makes LiteLLM huge is exactly the machinery this design gets to skip. NVIDIA, Groq, Ollama, vLLM, and self-hosted gateways all fall out of the same flag, concurrently, on one port. And `meter run --upstream nvidia=… -- python agent.py` wires the env var automatically, so the demo is one line.

## Constraints

- Backward compatibility is sacred: bare `/v1/messages` and `/v1/chat/completions` must behave exactly as today (default upstreams, `--anthropic-target`/`--openai-target` overrides intact).
- Passthrough invariants hold for prefixed routes: auth headers forwarded, never persisted; bodies never rewritten; SSE tee'd (client gets chunks immediately, capture in parallel).
- No config file. CLI flags only (open-source UX: one command, zero setup).
- `meter run` auto-wiring is per-provider-singular: `OPENAI_BASE_URL` is one env var, so `meter run` wires at most one OpenAI-dialect upstream per run.

## Premises (agreed)

1. **Dialect, not provider.** `integrate.api.nvidia.com` speaks the OpenAI chat dialect (same path, Bearer auth, same SSE shape) — `capture-openai.ts` parses it. "openai" generalizes to a *capture dialect* shared by many named providers.
2. **Interim unblock exists today.** `meter proxy --openai-target https://integrate.api.nvidia.com` works now; its defects are the "openai" labeling in run titles/logs and single-provider displacement.
3. **Routing is by URL prefix.** Concurrent providers are distinguished by provider-named base URLs (`http://127.0.0.1:8765/nvidia/v1/...`), single port. Bare paths stay backward-compatible.
4. **Existing distribution.** Ships as a normal `@meterbility/proxy` + `@meterbility/cli` change through the existing npm pipeline.

## Cross-Model Perspective

Codex (gpt-5.5, read-only cold read) independently converged on the same shape: repeatable `--upstream <name>:<dialect>=<url>` flag, dynamic prefix routes, `provider` stored separately from `captureDialect`, reuse `capture-openai.ts` for NVIDIA, bare paths unchanged. Its framing: "Meterbility becomes the neutral flight recorder for any OpenAI-compatible agent backend, not an Anthropic/OpenAI proxy with a few extra targets." It proposed the same five test cases adopted in Next Steps. No premise challenged.

Claude's one pushback on Codex's examples: upstreams that already carry a path segment (`https://api.groq.com/openai`, Ollama's `/v1`-only OpenAI surface) make path-join semantics the likeliest silent breakage — promoted to an explicit test in Next Steps.

## Approaches Considered

### Approach A: Label-fix stopgap — rejected
`--openai-label <name>` on the existing single-route design. Ships in ~30 min but supports one OpenAI-compatible provider per session and gets redone as B the moment concurrency matters. Rejected as a dead end (kept only as the *interim* unblock, which needs no code at all).

### Approach B: Named upstream registry + prefix routing
Repeatable `--upstream <name>[:<dialect>]=<url>` flag (dialect defaults to `openai`; `anthropic` allowed). Routes generated dynamically: `/<name>/<rest>` strips the prefix, forwards `<rest>` to the named upstream, captures with the dialect's parser, labels steps with the provider name. Bare paths keep today's behavior. Effort M (CC ~2-3h with tests); risk: path-join semantics, SSE tee through prefixed routes.

### Approach C: B + zero-config wiring via `meter run` — CHOSEN
Everything in B, plus `meter run` learns the same `--upstream` flag and auto-exports `OPENAI_BASE_URL=http://127.0.0.1:<port>/<name>/v1` (or `ANTHROPIC_BASE_URL` for anthropic-dialect) for the wrapped command. Effort M+ (CC ~3-4h); kills B's main con (users hand-typing prefixed URLs).

## Recommended Approach

**Approach C.** B is the smallest durable mechanism satisfying both stated needs (NVIDIA today, concurrent prefixed providers); C makes it invisible — the user never learns the prefix convention unless they want it. Both models independently converged on B's shape; C was chosen by the builder for UX completeness (10/10 vs 8/10).

Design details locked during the session:

- **Flag grammar:** `--upstream <name>[:<dialect>]=<url>`, repeatable. Parse by splitting on the **first `=`** (URLs contain colons — the left side is `name[:dialect]`, everything right of the first `=` is the URL). `<name>` is `[a-z0-9-]+` (underscores excluded by design, which keeps `__meter`-style internal segments uncollidable). Names are checked against two distinct sets: **built-ins** (`openai`, `anthropic` — pre-registered per decision 2A, so user registration fails as a duplicate) and **illegal path segments** (`v1`). `<dialect>` ∈ {`openai`, `anthropic`}, default `openai`. Upstream URLs must be http/https origins-plus-optional-path — a query string or fragment in the upstream URL is rejected. Malformed values are hard errors at startup, not warnings. Parser + validation are exported from `@meterbility/proxy` next to `startProxy`'s own input checks (decision 3A); the CLI is a thin passthrough and commander concerns stay in the CLI.
- **Library API (decision 1A):** `ProxyOptions` gains `providers?: Array<{name: string, dialect: "openai" | "anthropic", url: string}>`; the existing `upstreams` field keeps its exact current meaning (override a default provider). Two verbs, two fields, zero breakage.
- **Routing:** request path `/<name>/<rest>` where `<name>` is registered → forward to `<url>/<rest>`, preserving the query string (as `server.ts` does today) and joining carefully when the upstream URL itself carries a path segment (no double slashes, no dropped segments). **Everything** under a registered prefix forwards; capture is attempted only when `<rest>` matches the dialect's capture path (`/v1/chat/completions` or `/v1/messages`) — so `/nvidia/v1/models` passes through uncaptured rather than 404ing. Unregistered prefixes and bare paths fall through to today's PROVIDER_ROUTES matching. `/__meter/health` and the 404 message enumerate the dynamic route set, not the static table.
- **Provider label storage (REVISED in eng review, decision 5A — supersedes the tags approach):** provider becomes a **first-class nullable field** on both `Run` and `Step`: `provider?: string` in `@meterbility/shared` types, `provider TEXT` columns added via the collector's existing additive-migration helper (`ALTER TABLE ADD COLUMN` pattern, schema.ts:385), mirrored in `@meterbility/store-postgres`, threaded through `insertRun`/`insertStep`, and displayed in the web UI (run header badge). Existing rows stay `NULL` (no backfill; display falls back to nothing). Rationale: Codex outside voice named tag-convention re-inference as semantic debt; the user chose the honest domain model over blast-radius minimization. The run-title fallback uses the provider name (`nvidia · <model>`). REVISED (built, decision 2C): the upstream **host:port** IS persisted — `runs.upstream_host`, recorded at run creation — resolving the name-reuse ambiguity (same provider name against different URLs across sessions is now distinguishable). Host only: never path, query, or credentials. Shown in the provider badge tooltip. Verified live: `upstream_host: integrate.api.nvidia.com`.
- **Capture threading:** the route entry carries `provider` (the label, e.g. `nvidia`) separate from `dialect` (which capture module parses); the `CAPTURES` map re-keys from provider to dialect.
- **Run grouping:** `RunGrouper`'s seed gains the provider name — otherwise identical prompts to the same model name through two upstreams (the A/B comparison this feature exists for) would merge into one run. Provider enters `resolve()` as an optional parameter (or optional `ParsedRequest` field) with a default, so existing grouping tests pass untouched.
- **Auth/headers:** header behavior is unchanged — `forwardHeaders()` forwards all non-hop-by-hop, non-`x-meterbility-*` headers today, and prefixed routes do the same. `authHeaders` on the route entry is NOT a forwarding whitelist; it remains the never-persist redaction list.
- **Flag precedence (refined in eng review, decision 6A — provider-scoped overrides):** `--upstream` composes with the existing flags. `--openai-target`/`--anthropic-target` re-point the **default provider entity itself** — bare paths AND the symmetric `/openai/...`, `/anthropic/...` prefixes (decision 2A) both follow the override. One provider = one upstream, always; no flag combination can capture two different hosts under one provider label. In `meter run`, an openai-dialect `--upstream` wins `OPENAI_BASE_URL` over the bare default (same for anthropic); `--no-openai`/`--no-anthropic` suppress default-provider wiring but never named upstreams.
- **`meter run`:** accepts the same `--upstream` flag(s), starts/uses the proxy, and exports the prefixed base URL for at most one upstream per dialect (singular env vars); more than one same-dialect upstream in a single `meter run` is an error explaining the constraint. (Consequence: concurrent same-dialect providers in one session require hand-set env vars in the client processes — `meter run` alone can't wire both.)

## Open Questions

1. ~~Cost/display~~ RESOLVED (built, decision 1C): vendor-namespaced models (containing `/`) are **unpriced** — `costCents` returns 0 with an `unpriced` flag (the Opus-rate fallback would overstate an open 8B model ~100×; a plausible wrong number is worse than an honest unknown). Steps AND runs get `cost:unpriced` tags; web UI (run rows, fleet cards, run header) and `meter list` render "unpriced" instead of $0.00. Un-namespaced unknown models keep the frontier fallback + `cost:approx`. Verified live: NVIDIA run shows `cost:unpriced`, cost 0, tokens exact.
2. ~~Default providers reachable via prefix?~~ RESOLVED in eng review (decision 2A): yes, symmetric — `/openai/...` and `/anthropic/...` work; bare paths remain back-compat aliases.
3. ~~NVIDIA usage-field fidelity~~ RESOLVED empirically (live smoke, 2026-08-19, meta/llama-3.1-8b-instruct): NVIDIA returns `usage` on streams **by default** (no `stream_options.include_usage` needed), in a **separate final chunk with empty `choices: []`** after the finish_reason chunk; every delta carries `role`; `prompt_tokens_details.cached_tokens` is populated (maps to `cached_read`); an `nvext` vendor blob rides on every chunk. The real shape is pinned as the test fixture in server.test.ts. Both streaming and non-streaming capture verified end-to-end through the `/nvidia/` prefix: provider column set on run+step, tokens + cached + latency correct, cost flagged `cost:approx`.

## Success Criteria

- `meter proxy --upstream nvidia=https://integrate.api.nvidia.com` + `OPENAI_BASE_URL=http://127.0.0.1:8765/nvidia/v1` captures a real NVIDIA session with `provider = "nvidia"` on the run and every step (and title `nvidia · <model>`), token usage populated, streaming latency indistinguishable from bare-path proxying.
- Real OpenAI and NVIDIA traffic captured concurrently on one port in one session, correctly attributed, grouped into distinct runs even for identical prompts/models.
- All existing proxy tests pass unchanged (backward compat proven, not asserted).
- `meter run --upstream nvidia=… -- <cmd>` works with zero manual env vars.
