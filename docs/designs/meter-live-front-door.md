# Design: `meter live` — one-command front door for ingest + side-effect capture, with step-range file views

## Problem Statement

The founder asked for (1) one command that starts session ingest and file side-effect capture together, (2) a view of file changes at a single step, (3) a view of changes from step X to the current step. Code reading showed most of this shipped: `meter watch --files` (packages/cli/src/commands/watch.ts) already runs LiveInspector + FileSentinel in one process; `meter files <run> --at <step>` (packages/cli/src/commands/files.ts) covers per-step; `meter files --diff <path> --from/--to` covers ranges but only per-path.

The real problem, in the founder's own words: "I'm just forgetting to start a session or ingest one with watch at start / the flow is confusing currently." Three overlapping mechanisms (hook capture, sentinel, ingest) with no single front door, plus one genuinely missing query shape: an all-files range summary ("everything changed from step X to now"), including against a live run.

## Constraints

- Capture planes are frozen except additive, read-only instrumentation (timestamps/counters on FileSentinel for the health line — no semantics changes): v0.5.1 (cross-vendor parity) shipped days ago and the sell-track demo window is open. Otherwise composition only — LiveInspector, FileSentinel, files.ts renderers, hook_capture attribution.
- No silent always-on capture. Audit positioning: capture is credibility, not plumbing. Consent boundary is `meter init --hooks` (explicit, once); run-time may be automatic/nudged after that.
- Degraded capture must be visible, never silent (fseventsd starvation exists in the wild; founder's own Mac is the fixture).
- Ships in the existing @meterbility/cli npm package and release pipeline.

## Premises (agreed; #4 revised after cross-model challenge)

1. The primary problem is packaging/flow, not capture capability — one command starting ingest + capture together with self-explaining status.
2. The one missing query shape is the range summary: all files changed from step X to [Y | current], no path required. Per-step view exists and needs surfacing, not rebuilding.
3. Consent at init-time, automation at run-time: the hook plane may auto-ensure/nudge the live side. No silent always-on daemon. (Session eureka: the invisible-daemon consensus puts the consent boundary in the wrong place for an audit product.)
4. **(Revised per Codex challenge)** The "only additions" symptom gets a separate investigation (filed: likely host fseventsd coalescing), AND the front door ships a capture-health indicator so degraded capture is visible, never silent.
5. Build from shipped parts only; no new capture plane; v0.5.1 capture semantics frozen.
6. Distribution is solved: existing npm package + CI.

## Approaches Considered

### Approach A: Sharpen What Exists (minimal viable)
`meter watch` gets `--files` on by default + rewritten help/status text; `meter files` gains the range summary. Effort S, risk low. Rejected as the wedge: leaves "watch" as a verb you must remember — the named pain survives the fix. (Its range-summary piece is absorbed into B.)

### Approach B: `meter live` Front Door (ideal architecture) — CHOSEN
New command composing shipped parts. Spec below.

### Approach C: Hook-Ensured Always-Capture (creative/lateral)
Hook plane auto-spawns detached ingest+sentinel on first tool call; `meter live` becomes a pure viewer; forgetting becomes impossible. Effort L, risk high (daemon lifecycle, orphan processes, hook hot-path timeout budget). Deferred, not rejected: both models flagged skip-for-now during the demo window. B's nudge mechanism is designed so C can replace it without changing the viewer surface.

## Recommended Approach

**Approach B — `meter live`.** Both models converged on this shape independently. Composition of shipped parts; capture semantics untouched.

### Command spec

`meter live [run-id-or-prefix] [--provider auto|claude|codex|cursor] [--files-dir <path>] [--json] [--no-files]`

1. **Startup header (self-explaining status):** detected active session(s) (or "none yet — start your agent; I'll attach"), capture mode per runtime (hooks=exact / sentinel=fallback / both), watched file root + ignore sources, DB path, current step of each attached run. Loud, colored warning when no session is active — with the one next action to take. The header prints immediately; on a cold store the initial backfill runs in the background with a progress line ("backfilling N sessions…") so attach latency is independent of history size. Progress source: the CLI approximates via the session-discovery count + spinner in v1; a small additive progress event on LiveInspector is permitted if needed (ingest side, not the frozen capture plane).
2. **One process, both planes:** LiveInspector (incremental ingest) + FileSentinel (side-effect capture) started together, exactly as `watch --files` does today; `meter live` supersedes that flag pair as the blessed path. Concurrency policy: multiple `meter live` processes on the same root are allowed in v1 — the sentinel's blob-ref dedup (file_sentinel.ts insertChange) absorbs double-observation; residual duplicate-row risk under insert races is accepted and documented, no single-instance lock.
3. **Live stream:** per-step line `step 42 · Edit packages/cli/src/foo.ts · +12 −3` interleaved with run lifecycle events. `files:changed` events carry paths only, so the CLI fetches the step's FileChange rows on each event for the ± stats (cheap, indexed lookup). File rows cross-reference their step so the stream teaches the per-step query (`meter files <run> --at 42` printed as a hint on first file event). A `[run-id-or-prefix]` argument filters the *display* only — sentinel capture and ingest remain global (attribution is temporal-proximity across all in-progress runs; a filtered viewer must not silently discard captures for other runs).
4. **Capture-health line (premise 4):** periodic status line + degraded warning. Degraded is a cross-check, not a bare timer: file-touching steps were ingested within the window — counting only runs whose cwd overlaps the watched root (same `cwdOverlaps` predicate the sentinel uses for attribution, so a session editing a different repo can't fire a false warning) — AND no sentinel event arrived within the threshold (an idle repo is healthy, not degraded). Requires additive read-only instrumentation on FileSentinel: last-raw-FS-event timestamp and event counters, surfaced pre-debounce. On a starved host it must say so: "steps are editing files but no filesystem events for ≥15s — file capture degraded (host fseventsd) — hook-based capture unaffected."
5. **Range summary (the missing query):** `meter files <run-id> --from X [--to Y]` now valid WITHOUT `--diff` — renders the existing git-status-style collapsed summary (collapseByPath) restricted to the step window. `--to` omitted = latest ingested main-band step, which against an in-progress run means "to the current step" and re-runs cleanly as the run advances. Window semantics: sequences resolve against the main band only; synthetic-band steps (hooks 100k / admin 200k / checkpoints 300k) are excluded from the window match, and a footer line reports "N band-attributed changes outside the window match (hook/admin)" so excluded rows are visible, never silent. `--at` is mutually exclusive with `--from`/`--to` (error). `--json` supported. Reuses resolveStepSeqLoose/filterByStepSeq from files.ts.
6. **Hook nudge (premise 3, C-compatible seam):** `meter live` writes a heartbeat row (settings table, `live.heartbeat` = ISO timestamp) every poll tick. Any human-invoked `meter` command (exclusions: `capture`, `cursor-hook`, and `--json` invocations — hook hot paths and scripts) checks: watch/hook-derived FileChange rows inserted in the last 10 minutes AND heartbeat absent or staler than 2 minutes → print one line: "capture active on <run> — `meter live` to attach." Query is `LIMIT 1` (existence check); no covering index for `derived_from`+`created_at` today — add one only if it ever shows in CLI startup latency. No background process is spawned.
7. **`meter live --json`:** NDJSON, a superset of `watch --json` — same event objects, plus health as a typed event (`{"type":"capture:health","fs_event_age_ms":…,"ingest_lag_ms":…,"degraded":bool}`).
8. **`meter watch` disposition:** kept as the raw event-stream tool (JSON/scripting); its help text points humans at `meter live`. No breaking change in this ship.

## Open Questions

- Name check: `live` vs `attach` vs `tail` — decide before docs; `live` assumed throughout.
- Should `meter live` with no active session offer to backfill-ingest the most recent completed session (covers "forgot to start it" retroactively for ingest, though not sentinel capture)?
- Capture-health thresholds: what FS-event age counts as degraded (candidate: >5s warn, >15s degraded)? Calibrate on the founder's starved Mac vs a healthy host.
- Does `--provider` filtering earn its place in v1, or is cwd-scoped auto-detection enough?

## Success Criteria

- Cold start: one command from "agent is running" to first captured file-change line, under 60 seconds on a warm store, no docs consulted. On a cold store (first-ever run against a large `~/.claude/projects` history) the header and a backfill progress line appear immediately; the 60s target applies from backfill completion.
- Founder dogfood: 7 consecutive days where every real agent session on this machine was ingested+captured (the forgetting metric goes to zero or the nudge fires and recovers it).
- Range query: "what changed from step X to now" answerable in one command against a live run, all files, no path argument.
- Capture-health: on the founder's starved-fseventsd Mac, `meter live` visibly reports degraded file capture; on a healthy host it reports healthy. No silent degradation.
- Observation (assignment): one non-maintainer completes cold install → live capture → range query while the founder watches silently; stall points recorded.
